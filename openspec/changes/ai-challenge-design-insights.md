# AI 出题思路 —— 从真实 Debug 中提炼的挑战设计模式

## 来源

基于 `deep-research-agent` 项目 7 个 bug 的完整排查过程，结合作业流程思路.md 中 Step 11 的错误分类框架。

---

## 一、我们遇到的 7 个 Bug → 3 种错误类型

按作业流程 Step 11 的分类：

### 代码错误
| Bug | 表现 | AI为什么容易错 |
|-----|------|---------------|
| `stream_chat` IndexError | `chunk.choices[0]` 未检查空数组 | API 文档没说明最后一个 chunk 的 choices 为空，AI 默认假设总是有效 |
| Streamlit key 冲突 | `st.expander` 没有唯一 key | Streamlit 不报错、不警告，渲染静默失败。AI 不了解 UI 框架的隐式约定 |

### 思维错误
| Bug | 表现 | AI为什么容易错 |
|-----|------|---------------|
| `should_retry` 状态修改 | 条件路由函数修改了 LangGraph state | LangGraph 文档未明确禁止，但这是设计约束。AI 理解不了"隐式规则" |
| `task_id` 被 TypedDict 过滤 | LangGraph 静默删除不在 schema 中的字段，`emit` 检查 `if task_id:` 失败后静默跳过 | **最致命的模式：框架静默行为 + 代码静默失败**，两层静默叠加，排查极其困难 |

### 思考不够充分
| Bug | 表现 | AI为什么容易错 |
|-----|------|---------------|
| AsyncOpenAI + uvicorn 冲突 | 异步库在特定运行时环境中卡死 | AI 不会主动测试"库 × 运行时环境"的兼容性矩阵 |
| asyncio.Queue 不可靠传递 | 事件在单测中正常，在 StreamingResponse 中丢失 | AI 不会验证"数据结构在真实负载下的行为" |
| DeepSeek-V4-Flash 超时 | 特定模型接口间歇性不可用 | AI 不测试多个模型的稳定性差异，不设置合理的超时/重试 |

## 二、提炼的 6 种高价值出题模式

### 模式 1：框架静默行为（杀伤力最高）

**核心特征**：框架在不报错、不警告的情况下改变或丢弃数据，且业务代码用静默方式处理这个结果。

**出题公式**：
```
使用一个有 TypedDict/Schema 校验的框架
→ 在代码中传递一个 schema 之外的字段
→ 下游代码依赖这个字段做关键判断
→ 判断失败时不报错，只是静默跳过
→ AI 需要追溯到"为什么这个值没了"才能修复
```

**效果**：AI 会反复修改下游逻辑、添加日志、怀疑网络问题，很难想到是框架过滤了字段。

### 模式 2：多层异步系统的隐藏约束

**核心特征**：问题出在 5+ 层异步调用栈的某一层，单测每一层都正常，组合起来就出问题。

**出题公式**：
```
前端框架 → HTTP 客户端 → Web 服务器 → Agent 框架 → 异步库 → 外部 API
每一层单独测试都正常
→ 但在特定的事件循环/线程模型组合下出现死锁或数据丢失
→ AI 需要理解整个调用栈的异步模型才能定位
```

**效果**：AI 自然会逐层排查，每次单测都通过，陷入"修好了→还是不行"的循环。

### 模式 3：UI 框架的隐式约定

**核心特征**：UI 组件有隐含的规则（如 key 唯一性），违反时不报错，只是渲染静默失败。

**出题公式**：
```
使用 Streamlit/Gradio/React 等 UI 框架
→ 在循环/动态渲染中使用重复或缺失的组件标识
→ 框架不报错，只是某些组件不更新或不显示
→ 功能看起来"卡住了"但实际数据已就绪
```

### 模式 4：条件路由函数修改状态（框架反模式）

**核心特征**：框架的路由/决策函数应该是纯函数，但文档未明确说明。

**出题公式**：
```
使用有状态机/工作流/图执行的框架（LangGraph, Airflow, Temporal 等）
→ 在路由/分支函数中间接修改全局状态
→ 框架内部对"节点"和"边"的执行上下文不同
→ 状态修改在某个上下文中不生效或导致死锁
→ 换成"在节点中修改"就立即修复
```

### 模式 5：第三方库 × 运行时的兼容性矩阵

**核心特征**：库在常规 Python 脚本中正常，在特定 Web 服务器的事件循环中异常。

**出题公式**：
```
选择一个有兼容性细微差异的库（如 openai 的 AsyncOpenAI）
→ 在普通脚本中测试通过
→ 部署到 uvicorn/gunicorn/gevent 等特定服务器环境
→ 出现连接池耗尽、事件循环阻塞、超时等问题
→ 修复方案是换用更底层的库（如 httpx 直连）或调整事件循环配置
```

### 模式 6：API 不稳定性 × 缺乏降级策略

**核心特征**：外部 API 的特定端点或模型版本不稳定，代码缺乏超时/重试/降级。

**出题公式**：
```
使用一个外部 API（LLM、搜索、数据库等）
→ 其中某个特定参数组合（如 response_format=json_object）响应极慢
→ 默认配置没有合理的超时和重试
→ 请求挂起，整个服务阻塞
→ AI 需要：识别是 API 问题 → 添加超时 → 添加重试 → 考虑切换模型
```

## 三、组合出题策略

**最难的题目 = 模式 1 + 模式 2 组合**

```
框架静默删除字段（模式1）
+ 多层异步系统（模式2）
= AI 在错误的排查方向上花费数小时
```

我们的实际案例就是模式 1+2 的组合，7 个 bug 同时存在，排查了 5+ 小时。

**建议的题目设计流程**：

1. 选一个"有隐式约束的框架"作为基底（LangGraph, Streamlit, Airflow 等）
2. 注入 2-3 个"静默失败"的 bug（不报错、不崩溃，只是表现异常）
3. 其中至少一个 bug 涉及"框架过滤/修改数据"
4. 确保框架至少 4-5 层调用深度
5. `test_outputs.py` 设计为"函数级正确性 + 端到端行为验证"，不要只测试最终输出
6. 验证方式：找一个强模型（如 Claude 4.5 Opus）测试，如果它也需要多次尝试才能定位 → 难度合格

## 四、对应错误类型检查清单

在编写题目时，逐项检查能否触发 AI 的以下错误：

### 代码错误
- [ ] 是否有 API 返回值的边界情况（空数组、None、特殊字符）？
- [ ] 是否有框架组件的隐式约束（key 唯一性、生命周期、线程安全）？
- [ ] 是否有 shell 脚本的跨平台差异（macOS vs Linux）？

### 思维错误
- [ ] 是否有框架的"反模式"需要避开（如路由函数不应修改状态）？
- [ ] 是否有依赖的静默行为（字段过滤、默认值覆盖）？
- [ ] 问题的根因是否在 AI 的"常识假设"之外？

### 思考不够充分
- [ ] 是否有异步/并发场景需要考虑？
- [ ] 是否有外部依赖的不稳定性需要处理？
- [ ] 测试是否覆盖了边界条件（空输入、超大数据、超时）？
